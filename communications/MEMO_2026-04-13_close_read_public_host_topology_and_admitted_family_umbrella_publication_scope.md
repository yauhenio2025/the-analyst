## Decisions To Freeze

### 1. The delivery vehicle remains the current Critic-hosted frontend

This tranche should treat the Critic-hosted frontend as the delivery vehicle.

It should not reopen:

- standalone host extraction
- new consumer-host architecture
- analyzer-mgmt as the end-user Close Read product surface

### 2. The admitted family set is frozen

The public `Close Read` umbrella in this tranche should admit exactly:

- genealogy
- AOI thematic/result-backed family page
- concept analysis:
  - inferential
  - logical

It should not admit:

- concept `assumption`
- concept `semantic_field`
- concept `causal`
- concept `metaphorical`
- compose-from-intent under `Close Read`
- cross-concept
- any new family

### 3. Native family routes remain live

This tranche should not remove or obsolete the native routes.

It should preserve coexistence with:

- genealogy native routes
- AOI native routes
- concept-analysis native routes

### 4. The shared product-law baseline remains narrow

Across admitted `Close Read` families, the baseline should remain:

- result-backed reading/work
- provenance visibility
- capture mode
- `CaptureActionBar`
- routed destinations limited to:
  - `Arsenal`
  - `Research todo`

This tranche is not a generic operation-law redesign.

## Proposed Implementation Sequence

### Phase 0: source-align to deployed truth and actual deployment topology

Before changing code:

- fetch latest refs for `the-critic`
- inspect the deployed-source-aligned frontend routes and Render/static-site configuration
- verify and freeze which public host is actually serving:
  - the frontend
  - the API
- compare that intended topology against:
  - local `render.yaml`
  - public host behavior
  - the concept/API proof hosts currently in use

Do not assume that:

- `render.yaml` names are current deployment truth
- route-level `200` alone proves the admitted-family product surface is correct

Freeze the actual topology first.

### Phase 1: audit the public surface gap on the actual frontend host

Determine which of these is actually true:

1. the public frontend host already serves the admitted routes correctly and only needs documentary/browser proof
2. the routes are reachable but the admitted-family surface still carries stale copy or product-law drift
3. the routes are reachable but hydration/data/rendering still breaks on one or more admitted family pages
4. the current public host still serves stale frontend code despite the local route set

This phase should explicitly inspect:

- `render.yaml`
- `webapp/public/_redirects`
- `webapp/src/routes.tsx`
- the public host behavior on the admitted `Close Read` routes

Output:

- one short host-topology note
- one short public-surface diagnosis

### Phase 2: verify and, only if needed, publish/harden the admitted-family `Close Read` umbrella on the actual public frontend host

On the real public frontend host, verify these routes with browser truth:

- `/p/:projectId/close-read`
- `/p/:projectId/close-read/genealogy`
- `/p/:projectId/close-read/aoi`
- `/p/:projectId/close-read/aoi/:thinkerId`
- `/p/:projectId/close-read/concepts`
- `/p/:projectId/close-read/concepts/:conceptSlug`

Preserve:

- the bounded root genealogy deep-link compatibility redirect if it is already part of the local route law
- native family routes outside the umbrella

If any of those routes still fail in actual hydrated behavior, fix only the narrow publication/hardening seam required.
Do not widen the family set in this phase.

### Phase 3: normalize the admitted-family product law on the public surface

Once the routes are reachable, verify and only if needed harden:

- umbrella landing-card availability/status law
- family switcher/navigation consistency
- result-backed/provenance/capture baseline consistency
- stale genealogy-first or pre-admission copy that no longer matches the admitted-family umbrella law
- concept family restriction to:
  - inferential
  - logical
- native-route coexistence links where family-specific fuller workspaces still exist

This is not a generic shell unification project.
Family-specific page bodies may stay family-specific.

### Phase 4: rerun a bounded public-host proof only if code or deploy config changed

If Phase 2 or 3 required changes:

- re-verify the public admitted-family routes on the actual frontend host
- verify one project with usable results on all admitted families if available
- verify concept family detail pages over an analyzer-v2-backed concept specimen

If no code or deploy-config change was required, record the public-browser proof and do not reopen broader proof corridors.

3. the umbrella landing page clearly exposes the three admitted families:
