## Purpose

Freeze the first honest **multi-engine** `Close Read` boundary after the bounded genealogy-first pilot.

This memo is not:

- a standalone-host memo
- a generic multi-engine implementation scope
- a claim that genealogy and AOI already share one settled shell

Its job is to decide five concrete things before more product code is written:

1. exact included engine families
2. exact host surfaces/pages
3. exact baseline shared operation law
4. exact family-specific follow-on operations
5. exact deferrals

## Bottom Line

The genealogy-first `Close Read V1` pilot should now be read as:

- a successful bounded pilot
- a real host/runtime/product corridor proof
- not the settled shape of the larger `Close Read` product

The next honest product boundary is:

- `Close Read` as an umbrella area on Critic
- with family-specific pages beneath it
- first including:
  - genealogy
  - `anxiety_of_influence_thematic_single_thinker`

That boundary is intentionally broader than the genealogy-first pilot.
But it is still narrower than the full long-term vision:

- AOI is admitted
- logic / premise-scrutiny is not yet admitted
- compose-from-intent is not yet admitted into `Close Read`
- standalone-host questions remain deferred

## Why This Boundary Is The Right Next Step

Three things are true at once:

1. The bounded genealogy-first pilot was the right first move.
2. The original `Close Read` direction was broader than genealogy-only.
3. The next open question is now product boundary, not renderer/capture plumbing.

The live code and docs support that reading:

- the genealogy pilot now exists as a real `Close Read` page in Critic
- AOI already exists as a real result-backed host family on the same host
- the vision/dictation docs explicitly point toward a mixed-engine flagship

So the next stage should not be:

- more genealogy-only fallback shaping
- premature standalone-host planning
- premature generic “one shell for everything” implementation

It should be:

- one concrete multi-engine product boundary that the next coexistence implementation tranche can follow

## Decision 1: Exact Included Engine Families

The first admitted multi-engine `Close Read` families are:

- `intellectual_genealogy`
- `anxiety_of_influence_thematic_single_thinker`

They are admitted for different reasons:

- genealogy because it already anchors the bounded pilot and proves the current `Close Read` runtime corridor
- AOI because it is the strongest code-backed non-genealogy family already live on the same Critic host

The following are explicit near-term future admission lines, but **not** part of V1.5:

- logic / premise-scrutiny
- relation-web / argument-map style families
- other analyzer-v2 families with real result-backed host/runtime evidence

This memo therefore freezes:

- a dual-family `Close Read` boundary
- not a genealogy-only product
- not a generic all-family product

## Decision 2: Exact Host Surfaces / Pages

`Close Read` becomes an **umbrella area with family-specific pages**, not one prematurely unified shell.

This is the chosen coexistence model.

### Why this model is chosen

The current live shells are materially different:

- `/home/evgeny/projects/the-critic/webapp/src/pages/CloseReadPage.tsx`
  - thin, bounded, genealogy-specific reader shell
- `/home/evgeny/projects/the-critic/webapp/src/components/influence/AoiV2ThematicPanel.tsx`
  - richer, thinker-scoped, result-backed thematic work surface with its own controls and page assumptions

Trying to force those into one unified shell now would reopen unresolved questions about:

- result discovery symmetry
- summary/export behavior
- readiness law
- family-specific controls
- route semantics

So V1.5 should unify **umbrella identity and baseline law**, not fully collapse page shape.

### Exact page posture

The `Close Read` area should expose:

- one umbrella landing page at `/p/:projectId/close-read`
- one genealogy family page beneath that umbrella
- one AOI family page beneath that umbrella

The exact implementation path names may still be scoped in the next implementation memo, but the product/page model is frozen as:

- `Close Read` umbrella
- family-specific pages under it

### Route / nav transition posture

For V1.5:

- `Close Read` in nav should mean the umbrella area, not only the current genealogy pilot page
- existing native routes remain live:
  - `/p/:projectId/genealogy`
  - `/p/:projectId/anxiety-of-influence`
- those native routes are not removed or declared obsolete in this tranche

This keeps V1.5 honest:

- `Close Read` becomes the product umbrella
- Critic’s older family-native routes remain intact while coexistence is proven

## Decision 3: Exact Baseline Shared Operation Law

The shared baseline across admitted `Close Read` families is:

- result-backed reading/work surfaces
- provenance visibility
- capture mode
- capture-and-route
- routed destinations:
  - `Arsenal`
  - `Research todo`

This memo does **not** freeze one generic cross-family control set.
It freezes one baseline operational floor.

### What the host may assume across families

Across all admitted `Close Read` families, the host may assume:

- the family page is result-backed rather than purely launch-first
- rendered views may be consumed through the existing Critic `V2TabContent` / capture runtime
- `CaptureActionBar` remains the baseline routed action shell
- provenance remains visible where already supported

### What the host may not assume across families

The host may **not** assume:

- one unified eligibility law already exists
- one unified family-neutral route structure already exists below the umbrella
- one unified set of summary/export/launch controls already exists
- one unified analyzer-owned follow-up-operation contract already exists

So the shared baseline is:

- capture-and-route over result-backed reading/work surfaces

not:

- one already-converged generic `Close Read` substrate

## Decision 4: Exact Family-Specific Follow-On Operations

V1.5 must distinguish baseline shared law from family-specific admissions.

### Genealogy family

Genealogy remains admitted as:

- the bounded `Close Read` reading family already piloted in Critic

Its V1.5 admitted behavior remains:

- bounded reading surfaces
- provenance
- capture mode
- route to `Arsenal` / `Research todo`

This memo does **not** broaden genealogy into:

- full genealogy workspace parity
- broader genealogy run-management UI
- generalized non-`Close Read` genealogy controls

### AOI family

AOI is admitted as:

- result-backed thematic reading/work surfaces only

That means the V1.5 AOI family admission is anchored to the current thematic/result-backed AOI path, not the entire AOI app estate.

AOI is **not** admitted wholesale.

In for V1.5:

- thinker-scoped result-backed thematic reading/work surface
- existing capture/provenance/runtime behavior on that surface
- route to `Arsenal` / `Research todo`

Out for V1.5:

- `compose-from-intent`
- source-backed launch flows
- hypotheses page as part of `Close Read`
- report page as part of `Close Read`
- legacy thematic page as part of `Close Read`

This is the crucial tightening:

- AOI is the first admitted non-genealogy family
- but AOI admission does **not** mean “bring every AOI page under Close Read”

### Why compose-from-intent is deferred

`/home/evgeny/projects/the-critic/webapp/src/pages/AoiComposeFromIntentPage.tsx` and
`/home/evgeny/projects/the-critic/webapp/src/lib/composeFromIntentExamples.ts` prove that AOI has a live compose-from-intent line.

But that line is a different product family:

- source-backed launch
- planner/handoff aware
- not only result-backed reading

Admitting it now would widen V1.5 beyond the chosen baseline and would reopen:

- launch posture
- readiness law
- source-selection policy
- family-specific compose semantics

So V1.5 freezes:

- AOI result-backed thematic reading/work in
- AOI compose-from-intent out

### Logic / premise-scrutiny

Logic / premise-scrutiny remains an intended future admission line because the original dictation explicitly centers:

- premise testing
- weak-point identification
- clarification / follow-up questioning

But it is not admitted here because this memo is freezing the **first** multi-engine boundary, not the full intended product.

## Decision 5: Exact Deferrals

The following remain explicitly deferred:

- standalone `Close Read` host decision
- broader cross-host operationalization beyond the bounded Critic-hosted posture
- generic cross-family downstream operation law
- generic destination-policy convergence
- analyzer-owned unified follow-up-operation contract
- Book Modeler live integration
- logic / premise-scrutiny family admission
- relation-web / argument-map family admission
- AOI compose-from-intent admission into `Close Read`
- any claim that genealogy and AOI already share one settled shell
- any claim that existing family-native Critic routes should be removed now

One wording clarification matters here:

- Critic is already project-scoped
- what stays deferred is not project scoping itself
- what stays deferred is broader cross-host and broader generalized operationalization

## What This Memo Freezes About Nav And Product Identity

This memo freezes a product identity shift:

- `Close Read` is no longer only the name of the genealogy pilot page
- it becomes the umbrella name for the first multi-engine reading/work area

But it does **not** freeze a hard migration away from existing family-native Critic sections.

So the coexistence rule is:

- `Close Read` gains umbrella identity
- family-native sections can remain live while the umbrella is proven

That is the smallest honest way to broaden the product without overclaiming convergence.

## Why AOI Is The First Honest Next Inclusion

AOI is admitted next because the evidence is already real:

- `/home/evgeny/projects/the-critic/webapp/src/pages/AnxietyOfInfluencePages.tsx`
  already carries stable AOI routes and thinker-scoped page identity

  already names both genealogy and AOI as current host workflow families

So AOI is not being admitted because it is conceptually attractive.
It is being admitted because it is the strongest current runtime-backed second family.

## What This Memo Does Not Claim

This memo does **not** claim that:

- the genealogy-first pilot failed
- AOI is already harmonized with genealogy under one common shell
- `Close Read` should immediately absorb all AOI routes and capabilities
- the final multi-engine product boundary is now settled forever
- the long-term standalone-host question is answered

It claims only:

- the next honest product boundary after the genealogy-first pilot is a dual-family `Close Read` umbrella with family-specific pages
- genealogy and AOI are the first admitted families in that umbrella
- the shared baseline is result-backed reading/work plus capture-and-route to `Arsenal` / `Research todo`
- AOI compose-from-intent and broader family admission remain deferred
