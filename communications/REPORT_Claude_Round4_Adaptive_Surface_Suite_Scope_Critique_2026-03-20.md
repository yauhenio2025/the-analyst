# Claude Critique: Round 4 Adaptive Surface Suite Scope

Date: 2026-03-20
Scope memo under review: `communications/MEMO_2026-03-20_round4_adaptive_surface_suite_scope.md`

## Summary

The memo proposes a well-bounded and logically sequenced next step: coordinating two adaptive surface-family selectors on the same generic genealogy page. The strategic reasoning is sound -- round 3 proved single-surface adaptive selection; the next honest variable to isolate is multi-surface coordination. However, the choice of `genealogy_conditions` as the second adaptive target has a serious structural weakness that the memo does not acknowledge: the conditions surface relies on seven `genealogy_cop_*` child payloads, most of which use `transformation.type = "none"` and render from raw prose or minimally structured card grids, meaning the selector will likely have very thin structured signals to discriminate between the proposed `conditions_balance_sheet` and `conditions_path_dependency_matrix` families. This makes conditions a higher-risk second target than it first appears, and the memo should either commit to solving the signal-extraction problem explicitly or choose a second surface where structured signals already exist.

## Corrections Needed

1. **The conditions child payloads do not expose the structured counts the selector needs.** The memo declares that the conditions selector "must aggregate from the existing `genealogy_conditions` child payload family" and lists signals like `enabling_count`, `constraining_count`, `path_dependency_count`, etc. But examining the actual child view definitions (`src/views/definitions/genealogy_cop_enabling_conditions.json`, `genealogy_cop_path_dependencies.json`, etc.), all seven children declare `"transformation": {"type": "none"}`. Their `data_source.result_path` points at sub-keys of the `conditions_of_possibility_analyzer` engine output. The presentation pipeline for these children currently delivers either raw prose (for `genealogy_cop_counterfactual` and `genealogy_cop_synthesis`, which use `renderer_type: "prose"`) or card-grid items (for enabling/constraining/debts/alternatives, which use `renderer_type: "card_grid"` with `template_card`). Whether those card-grid payloads arrive as structured item arrays at the `ViewPayload.items` level depends on whether the presentation cache was populated by a prior transformation or compose step. The memo assumes these structured item counts are "already-built" and just need to be read. That assumption must be verified against a real genealogy job's presentation cache before it can be trusted. If the items arrays are empty or still prose blobs at selector time, the entire conditions selector collapses to a coin flip.

2. **The `conditions_path_dependency_matrix` family contract specifies a `table` renderer with six specific columns (`dependency_or_branch`, `source_work_or_chain`, etc.) that do not correspond to any field names in the existing authored child view definitions.** For comparison, the round-3 relationship selector worked because `genealogy_relationship_landscape` already had per-work structured items with fields like `relationship_type`, `relationship_strength`, `influence_channels`, `centrality_assessment` -- the selector could score and reshape those directly. The conditions children use different field schemas: `genealogy_cop_path_dependencies` uses `description`, `chain`, `if_absent`, `is_acknowledged`; `genealogy_cop_alternative_paths` uses `path_not_taken`, `branching_point`, `why_not_taken`, `implications`. The proposed `conditions_path_dependency_matrix` would have to synthesize rows across two different child payload schemas (path dependencies + alternative paths), which is a nontrivial data-merging step, not a simple deterministic selector.

3. **The memo claims two conditions families are enough to count as "genuinely different surface contracts."** But reading the contracts carefully, both families ultimately reformat the same seven child data sources -- they differ in which children are promoted and what renderer wraps them. The `conditions_balance_sheet` is essentially an accordion with the enabling/constraining/debts sections as card lists and synthesis/counterfactual as prose blocks. The `conditions_path_dependency_matrix` is a table built from path dependencies and alternative paths. These are meaningfully different reading surfaces, but the risk of them feeling like "same data, different container" is real -- especially since the underlying engine output (`conditions_of_possibility_analyzer`) is identical in both cases. The memo should acknowledge this risk explicitly.

4. **The trace requirement specifies `adaptive_surface_suite_selection` as a single stage with "one decision block per adaptive target surface."** But the existing trace machinery in `src/presenter/decision_trace.py` is structured around a linear stage pipeline. The current `adaptive_surface_selection` stage already assumes a single surface. Adding a suite-level stage that contains two sub-decisions will require either: (a) a new trace schema where one stage contains an array of selection blocks, or (b) two separate trace stages. The memo does not specify which, and the choice matters for trace consumers.

## What The Memo Gets Right

1. **The sequencing logic is correct.** Round 1 proved the contract boundary, round 2 proved regrouping, round 3 proved single-surface adaptive selection. The next missing variable genuinely is coordinated multi-surface selection. The memo does not skip steps.

2. **The decision to keep proof modes independent and non-stacking (`adaptive_genealogy_surface_suite_v1` does not require `bounded_dynamic_genealogy_v1` or `adaptive_relationship_surface_v1` to be active simultaneously) is disciplined and correct.** Stacking proof modes would make failure attribution impossible.

3. **The hard scope rules are honest.** Exactly two surfaces, deterministic selection, no new inference pass, Critic stays generic, no generalized framework. These are the right constraints for a proof that wants to stay bounded.

4. **Carrying forward the round-3 relationship-landscape families unchanged is the right call.** The dossier/comparison/field-map contracts are already proven. Reopening them would waste scope on re-proving something already closed.

5. **The explicit "Assumptions To Scrutinize" section at the end of the memo is good practice.** The memo correctly identifies that assumption #2 (existing `genealogy_cop_*` payloads expose enough structured signal) is the most critical risk. This critique confirms that assumption is indeed the weakest link.

6. **The strategic diagnosis that "two genealogy jobs can still feel too similar at the page level if only one major surface adapts" is empirically correct** and follows directly from the dynamic composition audit (`NEXT_SESSION_DYNAMIC_COMPOSITION_AUDIT.md`) which documented that every genealogy analysis gets identical 25-view trees regardless of content.

## Recommended Scope Adjustments

1. **Add an explicit prerequisite gate: verify structured signal availability on a real genealogy job before implementing the conditions selector.** Before writing any conditions-family selection code, the implementor should run `GET /v1/presenter/page/{job_id}` against the existing Varoufakis genealogy job and inspect the actual `genealogy_cop_*` child payloads to confirm: (a) enabling/constraining conditions arrive as item arrays with countable structured objects, (b) path dependencies arrive with parseable chain arrays, (c) alternative paths arrive with distinct item records. If the payloads are prose-only or structurally degenerate, the conditions selector cannot work as specified and the scope should pivot to a different second surface before investing implementation effort.

2. **If the structured-signal prerequisite fails, `genealogy_tactics` is a stronger alternative second surface.** The tactics view (`src/views/definitions/genealogy_tactics.json`) uses `renderer_type: "card_grid"` with `items_path: "tactics_detected"` and already carries per-tactic structured fields: `tactic_type`, `severity`, `description`, `idea_ids_involved`, `prior_work_references`, `current_work_evidence`, `assessment`. The dynamic composition audit documented concrete variance between corpora: Markus had 16 tactics with heavy `position_reversal` and `strategic_ambiguity`; Varoufakis had 12 with more even distribution. That variance is already present as structured item data with typed fields. A tactics-surface adaptive selector could plausibly distinguish between: (a) a "dominant tactic pattern" surface (when one or two tactic types account for most severity-weighted instances), (b) a "distributed tactic repertoire" surface (when tactics spread evenly across many types), and (c) a "evidence-heavy investigative" surface (when evidence trails are unusually dense). This would be structurally parallel to what the relationship selector already does -- score items, identify distribution shape, choose a family -- and would not require cross-schema data merging.

3. **If conditions remains the second surface, the `conditions_path_dependency_matrix` family should be simplified.** Instead of a table synthesized from two different child schemas (path dependencies + alternative paths), define the matrix as reading only from `genealogy_cop_path_dependencies` items, using the fields that schema already provides (`description`, `chain`, `if_absent`, `is_acknowledged`). This keeps the selector honest about what structured data it actually has. Alternative paths can be included as a supplementary section rather than merged into the same table rows.

4. **Specify that the suite-level trace should use a single `adaptive_surface_suite_selection` stage containing an array of per-surface decision blocks.** This avoids polluting the linear stage pipeline with multiple adaptive stages and keeps the trace structure consistent with the "one composition mode = one trace stage" pattern established in rounds 2 and 3.

## Verdict

**Approve after revision.** The strategic reasoning and sequencing are correct. The scope boundaries are honest. The core risk is that the memo's second adaptive target (`genealogy_conditions`) depends on an unverified assumption about structured signal availability that, based on the authored view definitions and their `transformation.type = "none"` declarations, is likely weaker than the memo implies. The memo should either:

(a) add an explicit structured-signal verification gate before implementation begins, with a named fallback target (`genealogy_tactics`) if conditions payloads prove too thin, or

(b) replace `genealogy_conditions` with `genealogy_tactics` outright, which offers comparable analytical weight, proven structured variance across corpora, and an item-level data shape that directly parallels the relationship-landscape selector pattern.

Either path preserves the core round-4 claim: coordinated multi-surface adaptive composition on the same generic route. The difference is whether the second surface requires solving a data-availability problem inside the proof, or whether the proof can focus cleanly on the coordination variable it set out to isolate.
