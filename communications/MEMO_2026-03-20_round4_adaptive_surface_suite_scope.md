## Current Program Position

As of 2026-03-20:

- round 1 proved the thin-host/shared-contract/artifact-reuse boundary
- round 2 proved bounded runtime regrouping on the generic genealogy route
- round 3 proved that one authored genealogy surface can become content-sensitive under explicit runtime surface-family contracts

What is still not true:

- two genealogy jobs can still feel too similar at the page level if only one major surface adapts

That matters because the big vision memos were never pointing at "one clever adaptive tab."

Round 3 moved in that direction, but it did not yet close it.

## Core Strategic Judgment

The right next proof is not:

- more AOI work
- more Critic host plumbing
- style-only polish
- generalized freeform page generation
- broad reactivation of dormant refinement machinery

The right next proof is:

- a bounded multi-surface adaptive composition proof on the same generic genealogy route

Round 4 should isolate one new variable:

- can analyzer-v2 coordinate more than one adaptive surface-family choice on the same page while the Critic still stays generic

That is the smallest next proof that materially advances the platform thesis after round 3.

## Recommended Proof Targets

Round 4 should target exactly two genealogy surfaces:

1. `genealogy_relationship_landscape`
2. `genealogy_conditions`

Why keep `genealogy_relationship_landscape`:

- round 3 already proved its selector is viable
- it is one of the highest-variance surfaces in perceived page shape
- it gives continuity so round 4 does not start from zero

Why add `genealogy_conditions`:

- it is a high-level interpretive surface, not a minor detail tab
- it already has a rich authored contract plus seven nested `genealogy_cop_*` child views
- it exposes multiple structurally distinct regimes:
  - enabling/constraining field
  - path dependencies
  - alternative paths
  - counterfactual reasoning
  - synthetic judgment
- if it adapts alongside relationship-landscape, the overall page will diverge more perceptibly across jobs than round 3 could prove

Named fallback if the conditions signal gate fails:

- `genealogy_tactics`

This fallback exists because the round-4 reviews correctly flagged one real risk:

- `genealogy_conditions` is strategically stronger, but only if the current top-level conditions payload exposes stable structured signal on real jobs

So round 4 should prefer `genealogy_conditions`, but it should not pretend that preference is unconditional before signal verification.

## Pre-Execution Verification Gate

Before implementation starts, verify on at least one real genealogy job that:

1. `genealogy_conditions.structured_data` is present on the top-level parent payload
2. the parent payload exposes the engine-level arrays:
   - `enabling_conditions`
   - `constraining_conditions`
   - `path_dependencies`
   - `unacknowledged_debts`
   - `alternative_paths`
3. `genealogy_conditions.structured_data.meta` is present or can be losslessly reconstructed from those arrays

This is the primary seam.

The selector should not begin by re-aggregating `genealogy_cop_*` child payloads unless the parent payload turns out to be insufficient.

If this gate fails on real payload inspection:

- do not force conditions anyway
- switch the second adaptive target to `genealogy_tactics`
- rename the proof token accordingly before code work starts

## Hard Scope Rules

### 1. Exactly Two Adaptive Surfaces

Round 4 should adapt exactly two top-level genealogy surfaces:

- `genealogy_relationship_landscape`
- `genealogy_conditions`

Do not add a third adaptive surface in this tranche.

### 2. Deterministic Selection Over Existing Structured Outputs

Both selectors must operate on already-built presentation payloads and child payloads.

They must not:

- add a new inference pass
- parse raw prose in the host
- depend on a new generalized planner

Relationship-landscape continues to read transformed relationship-card structure.

Conditions should read the top-level `genealogy_conditions` payload first:

- `payloads["genealogy_conditions"].structured_data`

Primary signal source:

- `meta`
- top-level engine arrays such as `enabling_conditions`, `constraining_conditions`, `path_dependencies`, `unacknowledged_debts`, and `alternative_paths`

Child `genealogy_cop_*` payloads are secondary convenience surfaces, not the primary selector seam.

The selector should read counts, presence, and already-structured fields from those payloads, not raw authored prose.

### 3. The Critic Host Stays Generic In Substance

Round 4 succeeds only if the Critic generic workspace continues to behave generically in substance.

It does not count as success if The Critic learns:

- genealogy-specific surface selection logic
- genealogy-specific route branching
- genealogy-specific deep-link rules

Small generic updates are acceptable, for example:

- one new proof-label string for the new `composition_mode`
- generic trace-label or proof-reason updates that reflect per-surface suite decisions

Those do not violate the thin-host claim as long as they remain generic and mode-driven.

### 4. The Proof Is Bounded, Not a General Framework

Round 4 should prove:

- coordinated adaptive surface selection for two concrete genealogy targets

It should not become:

- adaptive everything
- whole-page topology generation
- a cross-workflow adaptive framework

## Bounded Claim For Round 4

Round 4 should prove one bounded thing:

- analyzer-v2 can choose validated runtime surface families for two genealogy surfaces on the same generic route, using deterministic signals derived from already-built structured payloads, and the existing generic host can restore the resulting page unchanged

That claim is materially stronger than round 3 because the page-level result can diverge in more than one place.

### Surface B: `genealogy_conditions`

Round 4 should introduce exactly two runtime families for `genealogy_conditions`.

#### Family 1: `conditions_balance_sheet`

Use when:

- the conditions field is best understood as a balance between enabling and constraining pressures, with debts and synthesis carrying more weight than dense causal chains

Minimum contract:

- top-level renderer: `accordion`
- required sections:
  - `conditions_snapshot` via `key_value_table`
  - `enabling_pressures` via `mini_card_list`
  - `constraining_pressures` via `mini_card_list`
  - `unacknowledged_debts` via `mini_card_list`
  - `synthetic_judgment` via `prose_block`
  - `counterfactual_stakes` via `prose_block`

Required field mappings:

- `conditions_snapshot` is built from `structured_data.meta` and must include:
  - `overall_balance`
  - `enabling_conditions_count`
  - `constraining_conditions_count`
  - `path_dependencies_count`
  - `unacknowledged_debts_count`
  - `alternative_paths_count`
- `enabling_pressures` reads `structured_data.enabling_conditions` with:
  - `title_field = description`
  - `subtitle_field = condition_type`
  - `badge_field = essentiality`
  - `description_field = how_it_enables`
- `constraining_pressures` reads `structured_data.constraining_conditions` with:
  - `title_field = description`
  - `subtitle_field = constraint_type`
  - `badge_field = binding_force`
  - `description_field = how_navigated`
- `unacknowledged_debts` reads `structured_data.unacknowledged_debts` with:
  - `title_field = what_is_owed`
  - `subtitle_field = creditor_work`
  - `description_field = possible_reasons`
- `synthetic_judgment` reads `structured_data.synthetic_judgment`
- `counterfactual_stakes` reads `structured_data.counterfactual_analysis`

Intended reading shape:

- what made the trajectory possible
- what constrained it
- what remains owed or unresolved
- what the final synthetic judgment is

#### Family 2: `conditions_path_dependency_matrix`

Use when:

- path dependencies, alternative branches, and causal lock-in dominate the shape of the conditions surface

Minimum contract:

- top-level renderer: `table`
- required data shape:
  - multi-table container, not one merged flat row type
- required tables:
  1. `Path Dependencies`
  2. `Alternative Paths`

Required field mappings:

- `Path Dependencies` table reads `structured_data.path_dependencies` and normalizes rows to:
  - `description`
  - `chain_depth` derived from `len(chain)`
  - `chain_summary` derived from joining `chain`
  - `if_absent`
  - `is_acknowledged`
- `Alternative Paths` table reads `structured_data.alternative_paths` and normalizes rows to:
  - `branching_point`
  - `path_not_taken`
  - `why_not_taken`
  - `implications`

This family should not depend on cross-schema row merging with debts or synthesis prose. Those can remain available as authored deep dives.

Intended reading shape:

- a structured causal map of how the trajectory locked in and what branches remained available

At least one conditions family must use a different top-level renderer from the other. This requirement is satisfied by `table` vs `accordion`.

## Selector Signals And Trace Requirements

Round 4 needs inspectable suite-level diagnostics.

The minimum acceptable trace addition is:

- `adaptive_surface_suite_selection`

That stage should show one decision block per adaptive target surface with:

- `target_surface`
- `selected_family`
- `signal_summary`
- `rejected_families`
- `rationale`

Relationship signal summary should retain the round-3 pattern.

Conditions signal summary should include, at minimum:

- `overall_balance`
- `enabling_conditions_count`
- `constraining_conditions_count`
- `path_dependencies_count`
- `alternative_paths_count`
- `unacknowledged_debts_count`
- `counterfactual_present`
- `synthesis_present`

Preferred signal source:

- `structured_data.meta` when present

Required fallback:

- derive the same counts from the top-level arrays if `meta` is absent or incomplete

Suite behavior:

- if either selected family fails validation, presentation/page/result routes fail closed
- trace still returns diagnostics instead of disappearing

## In Scope

Round 4 includes:

1. one new proof-mode activation:
   - `composition_mode=adaptive_genealogy_relationship_conditions_v1`
2. one workflow only:
   - `intellectual_genealogy`
3. two adaptive target surfaces only:
   - `genealogy_relationship_landscape`
   - `genealogy_conditions`
4. one deterministic selector per target surface
5. one inspectable suite-level trace stage
6. explicit renderer/data validation for each selected runtime family
7. proof that the same generic Critic host route restores the result unchanged

## Out Of Scope

To keep this proof honest, the following remain out of scope:

- AOI adaptive composition
- adaptive composition for more than two genealogy surfaces
- whole-page topology regeneration
- generalized multi-workflow adaptive composition
- new workflow-specific host code
- broad renderer-library expansion
- reactivating dormant refinement or recommendation machinery as the primary mechanism
- new standalone app shells
- replacing the authored catalog

If round 4 starts turning into adaptive everything, the scope has drifted.

## Why This Is The Right Next Step

Round 1 proved the consumer boundary.

Round 2 proved upstream runtime regrouping.

Round 3 proved one adaptive surface family.

The next meaningful question is no longer whether a single tab can change.

It is:

- whether two high-leverage surfaces can change together in a deterministic, inspectable, upstream-controlled way while the generic route still holds

That is the right next test of the beautiful-by-default thesis.

## Test And Proof Expectations

The eventual execution plan should require, at minimum:

### Analyzer-v2

- suite-mode routing for manifest, presentation, refresh, single-view, and trace
- deterministic relationship-family selection still working under the new suite mode
- deterministic conditions-family selection from the top-level `genealogy_conditions` payload, with array-derived fallbacks when `meta` is absent or incomplete
- fail-closed validation for invalid suite-selected families
- suite-level trace diagnostics on both success and invalid proof mode

### The Critic

- no new workflow-specific host logic
- composition-mode threading through the shared bounded-v2 path
- successful restore on the generic route when both adaptive surfaces differ from authored baseline
- continued generic handling of proof-mode labels, freshness, and lazy single-view loading

### Proof Record

Round 4 should not count as closed without:

- at least two contrast genealogy jobs on the same route
- recorded selected family for both adaptive surfaces on each job
- trace evidence showing why the suite diverged

## Assumptions To Scrutinize

This memo is directionally confident, but these assumptions should be tested hard in review:

1. `genealogy_conditions` really is the best second adaptive surface
2. the top-level `genealogy_conditions` payload really does expose enough stable structured signal on real jobs to select conditions families without a new inference pass
3. two adaptive surfaces are enough to make page-level divergence meaningfully legible
4. the generic host can stay generic in substance with only small proof-label / trace-copy updates
5. suite-level trace is the right inspectability shape instead of separate per-surface stages

Those are exactly the questions the review prompts should challenge.
