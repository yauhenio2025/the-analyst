## Purpose

Turn the strategic audit into a clearer phased roadmap that keeps the program moving toward the real goal:

- analyzer-v2 owns analytical understanding, routing, planning, sequencing, and presentation law
- downstream apps are thin hosts, not workflow-specific analytical controllers
- the program stops spending disproportionate effort on local app minutiae that will be discarded once the host-neutral architecture exists

This memo is intentionally directional.

It is not a detailed scope memo for the next code slice.
It is a phase-ordering memo meant to keep the program from drifting into high-effort, low-strategic-value work.

## Core Strategic Decision

The audit supports one fixed direction:

1. finish the current AOI exemplar honestly enough to stop lying about platform readiness
2. then shift the main line of work away from AOI / `the-critic` blocker retirement and into host-neutral planner-to-presentation generalization
3. only after that define lifecycle semantics
4. only after that build broader governance and evaluation infrastructure

The main implication is simple:

- `the-critic` is a proving harness, not the destination architecture
- AOI is the first exemplar, not the platform itself
- current apps should only be repaired when the repair is required for honest proof, stable contract law, or reusable host behavior

## Phase-To-Stage Mapping Note

These phases are strategic buckets, not replacements for canonical stage numbers.

They intentionally cut across the canonical stage ledger:

- Phase 0 is mostly the last honest AOI exemplar gate inside current Stage 2 / Stage 5 work
- Phase 1 spans parts of Stage 7, Stage 8/9 follow-through, and Stage 13 because the real problem is the planner-to-presentation bridge plus host-contract ownership, not one isolated stage label
- Phase 2 is the stronger Stage 13 Tier B / broader bridge proof line
- Phase 3 corresponds to Stage 14 lifecycle work
- Phase 4 corresponds to Stage 15 governance/evaluation work

So “Phase complete” must never be read as “all underlying canonical stages are complete.”

## Anti-Drift Rules

These rules should govern what gets worked on from this point forward.

### Rule 1: Do not spend major effort polishing app-local behavior that is expected to disappear

Examples of low-priority work unless they directly unblock proof or contract law:

- AOI-specific UI polish
- page-local state choreography that will be replaced by host-neutral launch contracts
- custom current-app convenience behavior that does not encode reusable platform law

### Rule 2: Current-app work is justified only if it does one of three things

A change to `the-critic`, `aoi-canary`, or other current consumers is in scope only if it:

- unblocks an honest proof step that cannot otherwise be run
- codifies a stable host contract or host runtime rule that future consumers will also need
- removes host-owned analytical intelligence rather than adding more of it

If a proposed change does none of those, it should usually be deferred.

### Rule 3: Prefer upstream fixes over downstream compensation

When the same seam can be addressed in analyzer-v2 or in the host, prefer the analyzer-v2 side unless the host-side repair is clearly the stable contract boundary.

The program should not keep making the current apps smarter in order to preserve the slogan that analyzer-v2 is the brain.

### Rule 4: AOI-specific work must earn its keep

AOI-specific work is still allowed only while it is required to:

- close the current Stage 2 honesty gate
- preserve the AOI exemplar as a trustworthy reference case
- clarify a reusable planner-to-presentation or host-contract seam

Once that gate is closed, AOI-only repair is no longer the main line.

This rule is time-bound:

- Phase 0 gets one honest fresh post-fix rerun plus one explicit grade
- Phase 0 closes on the grade itself, not on whether the grade is flattering
- if the rerun still fails closure-grade, write the failure honestly and move the program forward instead of reopening open-ended AOI repair by default

### Rule 5: Apply the anti-drift filter before writing scope memos

Do not wait until after a bug is understood and a scope memo already exists.

Before writing any new scope memo outside an urgent operational fix, apply the prioritization filter in this roadmap first.

If the answer pattern is mostly “no,” the scope memo should usually not be written.

### Rule 6: Upstream AOI accretion is still drift if it deepens coupling

Not every analyzer-side change is real upstream progress.

If a proposed upstream change makes analyzer-v2 more AOI-shaped or more current-consumer-shaped without a clear generalization target, it is lateral drift, not architectural progress.

That applies even if the code technically moved “upstream.”

## Phase 1: Generalize The Planner-To-Presentation Bridge

### Goal

Move the main line from AOI-specific proof maintenance to reusable planner-to-presentation structure.

This is the real transition from “better bounded exemplar” to “actual architecture.”

### Why this is the first major post-exemplar phase

The audit identified the largest remaining architectural gap as:

- transient composition is still AOI-bound
- transient composition is still `the-critic`-bound
- task launch and Host Contract v1 still sit beside each other rather than inside one coherent lifecycle law
- analyzer planning truth still becomes presentation truth through an AOI-heavy handoff rather than reusable composition law

That means the next high-value work is not more consumer-specific repair.
It is de-AOI and de-`the-critic` generalization of the bridge itself.

### Phase 1A: Compose-entry and materialization de-coupling

This sub-phase is about the composition substrate itself.

Must land:

- remove hard structural dependence on `workflow_key == AOI_WORKFLOW_KEY` for transient composition entry
- remove hard structural dependence on `consumer_key == the-critic` for transient composition entry, or replace it with a narrower explicit abstraction that is not single-consumer glue in disguise
- replace AOI-shaped semantic dispatch with a reusable planner-to-presentation handoff contract rather than merely opening the old AOI entrypoints
- demonstrate at least one non-AOI materialization path through that contract

Must not widen:

- do not pretend removal of two validators is equivalent to generalization
- do not expose a nominally generic endpoint that still only knows how to compose AOI semantics internally

### Phase 1B: Host ownership decisions and contract unification

This sub-phase is about deciding what the host should still own.

Must land:

- one explicit ownership decision for source identity translation
- one explicit ownership decision for warm-snapshot / continuity-alias behavior
- one explicit ownership decision for surface selection
- one explicit ownership decision for navigation and launch-handoff semantics
- one explicit decision on whether `taskLaunchRuntime` becomes part of the host contract story or remains a separate bounded layer with named responsibilities
- clearer separation between:
  - host-neutral run/result/readiness law
  - composition-facing transient/source-backed law

### Phase 1C: Bounded router/planner generalization to support the new bridge

This sub-phase is about getting the planning substrate far enough beyond the current AOI/genealogy split to support the next proof line honestly.

Must land:

- enough router/planner generalization to support one non-AOI composition-facing path
- no hidden reliance on AOI-only handoff metadata where the new bridge claims to be reusable

Must not widen:

- do not attempt arbitrary open-ended workflow generation
- do not redesign the entire planner before one bounded non-AOI bridge exists

### Must not widen across Phase 1 overall

- do not attempt arbitrary open-ended workflow generation
- do not turn this into “make all current apps support everything”
- do not hide unresolved AOI assumptions behind a vague new generic endpoint

### Exit test

Phase 1 is complete only when all of the following are true:

- the transient/planner-to-presentation substrate is no longer structurally single-workflow-only
- the transient/planner-to-presentation substrate is no longer structurally single-consumer-only
- one reusable handoff contract exists that is not merely AOI semantic law behind weaker validators
- one non-AOI materialization path exists through that contract
- the program has explicit ownership decisions for source identity translation, warm snapshot / continuity alias behavior, surface selection, and navigation / launch handoff
- the relation between `taskLaunchRuntime` and Host Contract v1 is either unified or explicitly stabilized
- the generalized bridge remains browser-exercisable through at least one real integration path or one deliberate replacement harness

## Phase 2: Prove Host-Neutral Consumption Beyond The Current AOI Surface

### Goal

Earn a stronger proof that analyzer-v2 can drive presentation behavior beyond the current shells through one proof-only transient consumer contract plus one minimal harness, without rebuilding workflow-specific intelligence locally.

### Why this follows Phase 1

Trying to prove host-neutrality before the bridge is generalized would just force new consumers to re-encode current AOI/the-critic assumptions.

The right order is:

1. generalize the bridge
2. then prove another consumer or harness can consume it honestly

### Must land

- one non-AOI or more consumer-neutral composition-facing seam
- one stronger Stage 13 Tier B proof over transient behavior, not only result-backed rendering
- one proof that the same analyzer-owned planner-to-presentation discipline works across more than one workflow family or consumer surface

If a minimal ephemeral surface token or session identifier is required to make that proof honest, that narrow lifecycle decision may be borrowed early here without reopening full lifecycle law.

### Must not widen

- do not create a fake “generic host” that secretly embeds workflow intelligence in local glue
- do not keep adding special-case host rules for each consumer
- do not let result-backed proof substitute for transient proof where transient law is the actual question

### Exit test

This phase is complete only when the system can show that analyzer-v2 can drive a composition-facing experience beyond the bounded AOI / `the-critic` line without hidden consumer-local analytical reconstruction.

## Phase 3: Define Dynamic Surface Lifecycle

### Goal

Only after the bridge and host-neutral proof are stronger, define what dynamic analytical surfaces are as persistent objects.

### Why this is later

Lifecycle before bridge generalization would lock semantics around current bounded proof routes instead of around the intended platform.

### Must land

- explicit semantics for:
  - ephemeral launch
  - draft/session persistence
  - revisit
- clear ownership and retention rules
- clean separation between transient proof routes and durable user-facing dynamic surfaces

Default bounded Phase 3 target:

- explicit save from transient compose
- reopen by `session_id`
- no publish/share semantics yet

### Must not widen

- do not auto-promote every transient proof surface into a lifecycle object
- do not define lifecycle around the quirks of current app pages
- do not treat immutable `planning_decision_id` snapshots as if they were already user-facing lifecycle objects
- do not reopen new transient consumer registration before save/reopen law is explicit

### Exit test

This phase is complete only when one bounded lifecycle path exists on top of the more general planner-to-presentation substrate rather than as an AOI/the-critic special case, and that path supports explicit save plus reopen by `session_id` without rerunning planning or composition.

## Phase 4: Build Governance, Review, And Evaluation Infrastructure

### Goal

Make the generalized dynamic-planning system auditable and operable enough for broader platform claims.

### Why this is last

Governance should stabilize real architecture, not compensate for missing architecture.

### Must land

- reviewable traces for routing/planning/composition decisions
- bounded evaluation harnesses for routing, planning, readiness, and composition quality
- explicit human override or inspection seams where they are required

### Must not widen

- do not use governance as a substitute for contract clarity
- do not build heavy process around still-bounded AOI-only proof seams

### Exit test

This phase is complete only when governance sits on top of a genuinely more general analyzer-owned platform rather than just a complex AOI proving harness.

## Practical Prioritization Filter

Before accepting any future tranche or repair slice, ask four questions:

1. Does this move analytical decision-making upstream into analyzer-v2?
2. Does this reduce consumer-owned workflow-specific intelligence?
3. Does this generalize beyond AOI or beyond `the-critic`, or is it strictly required to finish Phase 0 honestly?
4. If we fully replaced the current app later, would this work still matter?

If the answer pattern is mostly “no,” the work is probably drift.

This filter is a gate, not a retrospective reflection.

Future scope memos should state explicitly that the filter was applied and why the proposed work passed it.

## Draft Judgment

The audit supports a fixed direction:

- use AOI only long enough to earn an honest exemplar judgment
- then move the program’s main line to generalization of the planner-to-presentation bridge and host-neutral consumption
- treat current apps as proving harnesses and contract consumers, not as the thing being perfected

If the program follows this order, the recent work becomes a strong foundation for the real analyzer-v2-as-the-brain vision.

If it does not, the program will likely keep accumulating clever local repairs in current apps without ever fully crossing into the intended architecture.
