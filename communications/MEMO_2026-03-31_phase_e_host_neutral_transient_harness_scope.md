## Purpose

Define the next broader bounded Phase E question now that the program has already live-proved:

- AOI `source_selection` on `aoi-canary`
- AOI `source_profile:dossier` on `aoi-canary`
- AOI `source_profile:comparison` on `aoi-canary`
- one bounded non-AOI genealogy `direct_sections` path on `aoi-canary`

The next honest question is no longer:

- another AOI preset broadening
- another route-family broadening inside `aoi-canary`
- another shell over the same `aoi-canary` contract
- or broad generic consumer registration architecture

It is:

- can the already-proved transient substrate now survive one explicit proof-only transient consumer contract plus one minimal harness over it, outside both the current-consumer page stack and the AOI-branded `aoi-canary` shell, without host-local analytical reconstruction?

The claim this slice would support must stay narrow:

- one proof-only transient consumer contract plus one minimal harness can consume one AOI transient path and one non-AOI transient path over analyzer-owned truth

not:

- broad analyzer-side generality
- broad generic consumer architecture
- broad host-neutral productization
- or proof that consumer identity no longer matters in general

## Current Code-Backed Boundary

### What is already true

Analyzer-v2 now has live-proved transient proof on:

- current consumer `the-critic`:
  - genealogy `direct_sections`
- second consumer `aoi-canary`:
  - AOI `source_selection`
  - AOI `source_profile:dossier`
  - AOI `source_profile:comparison`
  - genealogy `direct_sections`

The important current substrate facts are:

- analyzer transient admission for `consumer_key=aoi-canary` is already open on:
  - `source_selection`
  - `source_profile`
  - `direct_sections`
- the transient compose routes are already generic at the HTTP boundary:
  - they consume valid request bodies from any caller
  - they do not know which UI shell initiated the request
- `aoi-canary` already proves both major returned page-shape classes now relevant to a broader proof:
  - AOI `tab` root with one bounded raw-json leaf
  - genealogy `card_grid` root with empty raw-json leaf set
- the current direct-sections lineage is already analyzer-owned and planning-backed:
  - persisted `planning_decision_id`
  - analyzer-owned lowering into `ComposeFromIntentRequest`
  - final `compose-from-intent` request truth
- the current AOI source-selection lineage is already analyzer-owned and planning-backed:
  - persisted `planning_decision_id`
  - final `ComposeFromSelectionRequest` truth
- the existing `aoi-canary` client/render utilities are already structurally generic:
  - thin compose clients
  - structural page normalization
  - structural surface validation
  - generic `RendererHost`
  - generic `TabShell`

### What is still missing

The current missing seam is not analyzer admission on these two paths.

The current missing seam is:

- one explicit proof-only transient consumer contract that is not AOI-branded
- one minimal harness that proves the current client/render patterns are reusable outside the `aoi-canary` repo itself

Right now:

- `the-critic` still carries current-consumer runtime and proof-page assumptions
- `aoi-canary` still carries AOI-branded shell assumptions, even though it now has one bounded non-AOI path

So the broader remaining question is:

- can one proof-only transient consumer contract plus one minimal harness consume both one AOI transient path and one non-AOI transient path with no workflow-local intelligence, rather than only replaying those paths under the existing `aoi-canary` identity?

## Strategic Decision

The next bounded Phase E slice should vary the analyzer consumer contract and the proof vehicle together, while keeping both bounded and proof-only.

Keep fixed:

- analyzer-owned transient substrate
- current compose routes
- current request/response schemas
- the exact two already-proved path families:
  - AOI `source_selection`
  - genealogy `direct_sections`

Vary:

- one proof-only transient consumer contract
- one minimal harness over that contract

The exact recommended target is:

- one proof-only transient consumer definition:
  - suggested key: `transient-proof-harness`
- one minimal dedicated harness over that contract
- outside both:
  - the current `the-critic` proof-page stack
  - the AOI-branded `aoi-canary` app shell

The exact recommended proof cases are:

- AOI `source_selection`
- genealogy `direct_sections`

Why these two cases:

1. they already have analyzer-owned, planning-backed truth
2. they use different compose routes:
   - `compose-from-selection`
   - `compose-from-intent`
3. they produce materially different returned page shapes:
   - `tab`
   - `card_grid`
4. they avoid reopening the already-closed AOI `source_profile` preset work
5. together they are the smallest honest AOI + non-AOI pair for a proof-only consumer contract and harness proof

## Proposed Scope

### 1. One proof-only transient consumer contract

Add one explicit proof-only transient consumer definition that is separate from `aoi-canary`.

It should not be:

- AOI-branded
- product-oriented
- a generic open-ended consumer architecture
- a hidden alias of `aoi-canary`

It should be:

- proof-oriented
- explicit
- bounded to the renderer surface actually needed by this slice
- admitted only on:
  - `source_selection`
  - `direct_sections`

It should not broaden to:

- `source_profile`
- broader readiness law
- generic consumer/plugin registration

### 2. One minimal harness over that contract

Add one deliberate proof-only harness whose job is to consume analyzer transient truth honestly.

It should not be:

- a polished product app
- a third long-lived product shell
- an extension of the current `aoi-canary` shell
- another `the-critic` proof page

It should be:

- small
- explicit
- proof-oriented
- structurally generic at the render boundary

### 3. Fixture-backed inputs only

The harness should stay fixture-backed.

Use pinned analyzer-owned request truth copied from the already-proved lines:

- one fresh `ComposeFromSelectionRequest` fixture for the proof-only consumer
- one fresh `ComposeFromIntentRequest` fixture for the proof-only consumer

The harness must not:

- fetch planning decisions
- fetch analyzer lowering routes
- discover results
- derive requests locally
- reconstruct planner truth

It should replay pinned analyzer-owned request fixtures only.

### 4. Structural rendering only

The harness should render structurally, not semantically.

Required behavior:

- `tab` roots render through a tab/container path
- non-`tab` roots render directly through a generic renderer host
- AOI case preserves its pinned raw-json leaf set
- genealogy case preserves an empty raw-json leaf set

It must not:

- invent an AOI wrapper around genealogy output
- rewrite analyzer view meaning locally
- introduce workflow-branching beyond:
  - proof case selection
  - request dispatch to the correct existing compose route
- import from or depend on the `aoi-canary` repo

Important honesty note:

- the existing `aoi-canary` `transientClient.ts`, `RendererHost.tsx`, and `TabShell.tsx` are already structurally generic
- this slice should treat them as proof of reusable pattern shape, not as a dependency
- the new harness proves that those patterns can stand outside the `aoi-canary` shell

### 5. Fresh proof artifacts

The final proof artifacts for this slice must be fresh proof-consumer and harness artifacts, not recycled `aoi-canary` artifacts.

The current `aoi-canary` proof bundles should be treated as:

- analyzer-owned source material
- fixture lineage anchors

not:

- the final proof artifact set for this next slice

The next slice should freeze:

- one analyzer proof bundle for the AOI case under the proof-only consumer
- one analyzer proof bundle for the genealogy case under the proof-only consumer
- one harness proof note
- one JSON summary for the AOI case
- one JSON summary for the genealogy case
- screenshots
- HAR/session evidence
