## Purpose

Sharpen the roadmap now that the strategic intent is no longer only:

- keep proving genericity honestly

but also:

- move intentionally toward building `Close Read`

This memo still does **not** justify jumping directly to full `Close Read` productization.
It recalibrates the remaining corridor now that the `SubRenderers` adoption step is complete.

## The Core Recalibration

The current roadmap is directionally correct, but too loose in one important way:

- it treats `Close Read` as the best flagship proving ground
- yet it still leaves the path from current Phase E work to a first real `Close Read` build too implicit

That is no longer enough if the product intent is affirmative.

The corrected reading should be:

- `Close Read` is not the immediate next code slice
- but it **is** now the explicit near-term product target the remaining Phase E slices should be optimized toward

So the roadmap should stop sounding like:

- platform generality first, product later

and instead sound like:

- finish the minimum honest substrate corridor required to scope and then build a lean `Close Read V1`

## What Should Not Change

This recalibration does **not** justify jumping straight to full `Close Read` productization.

The earlier warnings remain correct:

- first-hop routing must stay distinct from destination-internal lifecycle
- workflow-neutral destination taxonomy is not ready
- generic renderer-package law is not solved
- full package convergence is not done
- Critic-local first-hop/workflow/type policy is not shared law
- the current host still consumes a packed `renderers-ui` artifact rather than the source tree directly
- host-side first-hop policy is still split across raw package capture, `currentRendererCapture`, and a universal `CaptureActionBar` that does not honor `allowed_destinations`

So the roadmap should not pretend that a full multi-user, multi-project `Close Read` app is the next memo.

## The New Honest Corridor

The roadmap should now describe a short, explicit corridor:

### Corridor Step 1

The dominant deferred shared capture-builder surface is now complete:

- bounded `renderers-ui` `SubRenderers` capture-base shell adoption

What that completion now means:

- the smaller package-native shell is proven across both the top-level trio and the current inline `SubRenderers` builders
- the remaining uncertainty is no longer utility fit on the dominant package-local builder surface
- the remaining uncertainty is the nested runtime-forwarding line itself

### Corridor Step 2

The forwarding decision gate is now also complete:

- `AccordionRenderer` still has a field-defaulting asymmetry:
  - nested capture can still appear, but forwarded `_captureSourceType` / `_captureEntityId` may silently fall back to package defaults
- `CardRenderer` still has a functional-availability asymmetry:
  - nested subsection sub-renderers do not receive capture runtime at all, so nested capture buttons are absent on that path

The decision verdict is now:

- those remaining asymmetries were **not** acceptable for the near-term `Close Read` surfaces that materially matter
- one bounded forwarding-normalization slice was therefore required next

This keeps the corridor honest:

- the package-internal decision gate is now closed
- the answer is `patch required`
- that required package-source patch is now also landed locally
- but the current host still consumes a stale packed `renderers-ui` artifact

### Corridor Step 3

The bounded `renderers-ui` release-artifact refresh plus focused Critic host-verification slice is now also complete.

That completion now means:

- the local forwarding patch is packed into a traceable `0.6.6` artifact
- Critic now consumes that refreshed tarball on the live host path
- the material nested genealogy consequences are already cleared on real installed-package proofs for:
  - `genealogy_target_profile`
  - `genealogy_per_work_scan`

So the remaining gap is no longer renderer-substrate drift between local package truth and current host truth.

What this still does **not** settle:

- Critic-local first-hop/workflow/type law
- product-layer destination policy
- broader host-delivery posture
- generic renderer-package capture law

### Corridor Step 4

Then scope a **lean `Close Read V1` product memo**.

That memo should stay bounded to what the runtime evidence already supports:

- first-hop operations only
- current real destinations only:
  - Arsenal
  - Research todo
- current rendered analysis families with real follow-up value
- current real output/UI patterns, not speculative universal ones

But that memo must also answer two product-layer questions the package work does not settle on its own:

- what app-level first-hop eligibility policy will gate visible capture operations, since the raw package utility does not consume `_firstHopAffordance`
- what host-delivery posture will be used, given that the current proved delivery path is still Critic plus a local packed `renderers-ui` artifact workflow and host-side capture policy is still split across multiple seams

It should explicitly defer:

- destination-internal lifecycle unification
- Book Modeler integration
- workflow-neutral destination taxonomy
- full multi-user / multi-project architecture
- generic downstream operation law
- generic renderer-package capture law

## What A Lean Close Read V1 Should Probably Mean

The roadmap should now bias toward a first product memo shaped like:

- one app for close reading of one or more related texts
- bounded analysis-family mix, defaulting first to genealogy-centered surfaces
- AOI or premise-scrutiny-style expansion only where code-backed runtime evidence materially strengthens the first V1 rather than merely broadening it
- grid-like or panelized output access across a few proven renderer families
- first-hop follow-up operations routed into current real destinations
- Arsenal and Research as the proven operational backbone
- one explicit app-layer capture-eligibility policy rather than inherited assumption that package-level capture availability alone is sufficient

Not:

- a universal downstream operating system
- a settled lifecycle/taxonomy platform
- a fully generalized super-app on day one

## Strategic Consequence

The main strategic consequence is simple:

- the renderer-substrate corridor is now clear enough to stop treating product scoping as premature
- the current next slice is now the first product-facing scope move, not another renderer/package repair

That is a meaningful sharpening.

It means the program is no longer only asking:

- what is the next honest generality proof?

It is also now asking:

- what is the minimum remaining honest work before a lean `Close Read V1` can be scoped and built?

## Recalibrated Bottom Line

The roadmap should now read as:

1. the dominant deferred package capture surface is complete
2. the forwarding decision gate is complete, and its verdict is `patch required`
3. the bounded forwarding-normalization implementation is also complete in local package source
4. the bounded release-artifact refresh plus focused Critic host-verification slice is also complete on the live host path
5. write one lean `Close Read V1` scope memo grounded in runtime-real first-hop operations and already-proved output families, while explicitly resolving host-delivery posture and app-layer first-hop eligibility policy

That is the sharper path toward actually building `Close Read`.
