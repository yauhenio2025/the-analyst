Date: 2026-03-21
Program: Thin Consumer Platformization

## Current Program Position

The host boundary is now well-established:

- the Critic generic route is a real thin-consumer proving vehicle
- adaptive composition can be threaded through the shared bounded-v2 path without workflow-specific host logic
- analyzer-v2 now carries adaptive proof modes for both genealogy and AOI

But one meaningful doubt remains:

- coordinated adaptive suite behavior has only been proven inside genealogy

Round 5 changes the shape of the remaining question. The open problem is no longer:

- can adaptive composition generalize across workflows at all

The open problem is now:

- can coordinated multi-surface adaptive composition also generalize across workflows, rather than staying a genealogy-only suite success story

That is the next variable to isolate.

## Core Strategic Judgment

The next proof should not be:

- another genealogy-only expansion
- a second single-surface AOI proof
- a generalized adaptive registry
- bespoke AOI-panel integration
- host-side AOI customization
- platform-wide app-on-the-fly generation

The next proof should be:

- the first **AOI child-surface adaptive suite** on the existing generic AOI route

Round 6 should isolate one bounded question:

- can analyzer-v2 coordinate adaptive family selection for more than one AOI child surface under the same parent container, on the same thin host boundary, without becoming genealogy-specific in disguise

That is the smallest next proof that materially advances the platform thesis after round 5.

## Recommended Adaptive Targets

Round 6 should target exactly two AOI child surfaces:

1. `aoi_by_theme`
2. `aoi_thematic_report`

### Why Keep `aoi_by_theme`

`aoi_by_theme` should remain the first target because round 5 already established it as:

- a high-salience AOI reading surface
- a stable grouped-payload seam
- the first successful AOI adaptive child-surface target

Round 6 should reuse that work rather than redefining the first AOI target again.

### Why Add `aoi_thematic_report`

`aoi_thematic_report` is the right second AOI target because:

1. it is a high-salience closeout surface, not a secondary regrouping axis
2. it comes from a distinct phase-4 structured payload rather than the same phase-3 finding regrouping
3. it proves coordination across **unlike AOI child surfaces**, not just two views over the same finding list
4. it keeps the proof bounded inside the existing AOI tab container

### Why Not Use `aoi_by_sin_type` As The Default Second Target

`aoi_by_sin_type` remains a legitimate later target, but it is not the recommended round-6 second surface because:

1. it is another regrouping of the same finding family already exercised by `aoi_by_theme`
2. it is less strategically valuable than proving coordination between a grouped thematic reading surface and a structured closeout report
3. it risks making round 6 feel like a second phase-3 findings proof rather than a broader AOI suite proof

Named fallback if the `aoi_thematic_report` gate fails:

- `aoi_by_sin_type`

That fallback is documentary first, not an execution-time improvisation:

- if Gate B fails, stop this branch
- write a short memo correction that makes `aoi_by_sin_type` the second target and defines its runtime families
- do not silently swap targets inside the implementation pass

## Pre-Execution Verification Gates

Round 6 should not proceed to implementation without verifying **both** candidate seams on the same two candidate AOI proof jobs or fixtures intended for final proof.

### Gate A: `aoi_by_theme`

Verify the round-5 seam remains stable:

- `_section_order`
- `_section_titles`
- one theme object per section id
- the existing seven per-theme fields
- findings cards with `title`, `subtitle`, `description`, `badge`, `sin_type`, `sin_type_label`

### Gate B: `aoi_thematic_report`

Verify `payloads["aoi_thematic_report"].structured_data` exists and stably exposes:

- `summary`
- `engagement_pattern`
- `key_divergences`
- `sin_distribution`
- `reading_implications`

And verify:

- `key_divergences` is a list, and every item is a dict with at least:
  - `title`
  - `description`
- `sin_distribution` is a list, and every item is a dict with at least:
  - `sin_type`
  - `count`
- if present, preferred `key_divergences` item shape is:
  - `title`
  - `subtitle`
  - `description`
  - `badge`
- if present, preferred `sin_distribution` item shape is:
  - `sin_type`
  - `count`
  - `description`

Treat these as Gate-B failures:

- `key_divergences` is prose rather than a list
- `key_divergences` is a mixed list rather than a list of dicts
- `sin_distribution` is prose rather than a list
- `sin_distribution` is a mixed list rather than a list of dicts
- required keys are missing from the emitted dicts

If Gate B fails on real payload inspection:

- do not force `aoi_thematic_report` anyway
- stop the branch before code work starts
- switch the second target to `aoi_by_sin_type` in a short memo correction
- rename the proof token accordingly before code work starts

## Hard Scope Rules

### 1. Exactly Two Adaptive AOI Child Surfaces

Round 6 should coordinate exactly two AOI child surfaces:

- `aoi_by_theme`
- `aoi_thematic_report`

Do not add a third AOI adaptive surface in this tranche.

### 2. Deterministic Selection Over Existing Structured Outputs

The suite must operate over already-built presentation payloads.

It must not:

- add a new inference pass
- reopen AOI engine contracts
- parse host-side prose
- introduce a workflow planner

### 3. Keep The Host Generic

Allowed host-side work:

- one new generic proof-label mapping for the new composition mode
- generic proof-route tests covering the new mode token

Not allowed:

- workflow-specific renderer logic in `AnalysisWorkspacePage`
- AOI-specific adaptive logic in the host
- bespoke-panel AOI proof work

### 4. Keep AOI Routing And Thinker Scope Stable

Do not reopen the round-1 AOI generic-route contract.

The round-6 proof must still use:

- `selected_source_thinker_id` as authoritative thinker scope
- the existing generic AOI restore/discovery rules

### 5. Name The Backend Expansion Honestly

Round 6 is not just a new constant.

It reopens one bounded but real expansion:

- the AOI adaptive path must grow from one adaptive child-surface decision to a coordinated AOI suite decision
- trace reconstruction must carry more than one AOI child-surface decision under a suite grammar
- unlike round 4, which coordinated top-level genealogy surfaces, round 6 must coordinate two child-surface rewrites under the existing `aoi_thematic_analysis` parent while preserving `source_parent_view_key` on both and leaving the parent container untouched

This is still bounded work, but it should not be misdescribed as trivial.

## Recommended Runtime Families

Round 6 should keep the existing `aoi_by_theme` families from round 5:

1. `aoi_theme_dossier`
2. `aoi_theme_comparison_review`

Round 6 should add exactly two `aoi_thematic_report` families.

### Family 1: `aoi_report_briefing`

Use when the report reads primarily as an interpretive closeout.

Contract:

- renderer: `accordion`
- top-level structured data contains:
  - `suite_summary`
  - `summary`
  - `engagement_pattern`
  - `reading_implications`
  - `key_divergences`
  - `sin_distribution`
- section order:
  1. `suite_summary`
  2. `summary`
  3. `engagement_pattern`
  4. `reading_implications`
  5. `key_divergences`
  6. `sin_distribution`

Section renderers:

- `suite_summary -> prose_block`
- `summary -> annotated_prose`
- `engagement_pattern -> annotated_prose`
- `reading_implications -> annotated_prose`
- `key_divergences -> mini_card_list`
- `sin_distribution -> mini_card_list`

Deterministic `suite_summary` rule:

- if `key_divergence_count > 0`:
  - `"{key_divergence_count} key divergences are distributed across {sin_distribution_count} sin categories, so the report is rendered as a briefing-led closeout."`
- otherwise:
  - `"The report is rendered as a briefing-led closeout because the prose sections dominate the available structured evidence."`

Intent:

- the AOI report should read as an editorial briefing with evidence carried later in the surface

### Family 2: `aoi_report_evidence_review`

Use when divergence cards and sin-distribution evidence are dense enough that comparison is more useful than prose-first sequencing.

Contract:

- renderer: `table`
- top-level structured data is a multi-table container:
  - `{"tables": [...]}`
- required tables:
  1. `Report Snapshot`
  2. `Key Divergences`
  3. `Sin Distribution`

Recommended table contracts:

- `Report Snapshot`
  - one row
  - columns:
    - `{ "key": "summary_excerpt", "label": "Summary", "sortable": false }`
    - `{ "key": "engagement_excerpt", "label": "Engagement Pattern", "sortable": false }`
    - `{ "key": "implications_excerpt", "label": "Implications", "sortable": false }`
  - rows:
    - one derived row with:
      - `summary_excerpt`
      - `engagement_excerpt`
      - `implications_excerpt`
- `Key Divergences`
  - columns:
    - `{ "key": "title", "label": "Divergence", "sortable": true }`
    - `{ "key": "subtitle", "label": "Theme", "sortable": true }`
    - `{ "key": "description", "label": "Description", "sortable": false }`
    - `{ "key": "badge", "label": "Severity", "sortable": true }`
  - rows:
    - one normalized row per `key_divergences` card
- `Sin Distribution`
  - columns:
    - `{ "key": "sin_type", "label": "Sin Type", "sortable": true }`
    - `{ "key": "count", "label": "Count", "sortable": true }`
    - `{ "key": "description", "label": "Description", "sortable": false }`
  - rows:
    - one normalized row per `sin_distribution` item

Excerpt derivation rule for `summary_excerpt`, `engagement_excerpt`, and `implications_excerpt`:

- start from the source prose value stripped of outer whitespace
- if empty, use `"—"`
- if length `<= 160`, use as-is
- if length `> 160`, use the first `157` characters plus `...`

Intent:

- the AOI report should read as an evidence-led review rather than a prose-first briefing

At least one report family should use a different top-level renderer type. That requirement is satisfied by:

- `accordion` vs `table`

## Recommended Deterministic Selectors

### Selector A: `aoi_by_theme`

Reuse the existing round-5 selector without redesign.

### Selector B: `aoi_thematic_report`

Compute, from the top-level `aoi_thematic_report` payload:

- `key_divergence_count`
- `sin_distribution_count`
- `non_empty_prose_sections`
- `summary_length`
- `engagement_pattern_length`
- `reading_implications_length`

Recommended rule:

- choose `aoi_report_evidence_review` iff:
  - `key_divergence_count >= 4`, and
  - `sin_distribution_count >= 3`
- otherwise choose `aoi_report_briefing`

This selector is valid only after Gate B shape validation has already passed. It should not attempt to infer counts from prose-shaped or structurally degenerate report sections.

This keeps the first AOI suite proof bounded and inspectable.

It does not try to prove a broad AOI report taxonomy.
