## Purpose

Define the next honest tranche after the recent translated-artifact-authority implementation work.

This tranche is **not** about inventing new architecture from zero.
It is about closing the current corridor cleanly and defensibly.

The system is now far enough along that the honest next move is:

- run a fresh post-fix live proof
- verify the same artifact identity across analyzer-v2, analyzer-mgmt, and the-critic
- fix only the narrow seam that fails if any part of that proof breaks
- then write the completion memo and roadmap update

## Bottom Line

The next tranche should be treated as a **live closeout tranche** for concept translated-artifact authority.

What is already substantially true:

- analyzer-v2 already has the translated-artifact authority route live
- analyzer-v2 already supports exact-run and latest-validated lookup
- the-critic already reads through analyzer-v2 authority for the admitted seam
- the-critic already exposes `_artifact_authority` metadata on readback
- analyzer-mgmt job pages are the correct operator proof surface for this seam, but the concept-artifact display should still be treated as build-and-verify rather than assumed fully sufficient

What is not yet cleanly frozen in the docs:

- a fresh brand-new project proof after the final authority-url and canonical-concept fixes
- a paired fresh proof for both admitted modes:
  - `logical`
  - `inferential`
- explicit confirmation that fresh inferential closeout is genuinely new proof work rather than a redundant rerun
- a browser-backed operator proof on analyzer-mgmt for those same fresh jobs
- the completion memo and roadmap update that would allow this corridor to be treated as fully closed

So the next honest move is not new feature expansion.
It is to close the current corridor correctly.

## Key Decisions To Freeze

### 1. Treat this as closeout, not greenfield

Do not write this tranche as if analyzer-v2 translated-artifact authority still needs to be invented from scratch.

Start from deployed reality:

- the route exists
- the route works
- the-critic read-through exists
- analyzer-mgmt job-level concept artifact inspection exists in bounded form, but the closeout tranche should still be prepared to extend that job surface if the browser proof shows required concept fields are missing

### 2. Use a brand-new live proof project

Do not reuse the April 9 specimen as the closing proof.

Use a brand-new project id in the form:

- `cutover-concept-artifact-closeout-<UTC-yyyymmdd-hhmmss>`

This avoids passing the tranche by reading stale artifacts or stale local mirrors.

### 3. Exact proof must use exact analyzer-v2 job lookup

For the final proof path, exact artifact lookup must use:

- `consumer_key`
- `external_project_id`
- `concept_name`
- `analysis_mode`
- `analyzer_v2_job_id`

The latest-validated lookup should still be verified, but it is a secondary confirmation path, not the primary proof path.

### 4. the-critic must remain fail-closed on authority mismatches

For the admitted seam, the-critic must fail closed if analyzer-v2 returns:

- no artifact
- non-passed validation
- mismatched `analysis_mode`
- mismatched `concept_name`
- mismatched `consumer_key`
- mismatched `external_project_id`
- mismatched `analyzer_v2_job_id`
- missing or wrong analyzer-v2 provenance

No local recomposition fallback is in scope for `inferential` or `logical`.

### 5. Keep scrutiny host-local and bounded

Do not reopen scrutiny architecture in this tranche.

The only scrutiny work in scope is:

- one fresh `quick` scrutiny run on the fresh logical proof artifact
- only as a downstream regression check that the analyzer-v2-backed logical read path still supports host-local scrutiny

### 6. analyzer-mgmt job pages are the operator proof surface for this tranche

Do not require implementation/detail pages to become artifact examples in this tranche unless the job-page proof shows a concrete gap that truly requires that work.

For this closeout slice:

- job pages are the operator proof surface
- implementation pages may remain composition metadata surfaces

## Implementation Sequence

### Phase 1: baseline verification and source alignment

Before launching anything new:

1. verify the current baseline specimen still reads correctly live
2. identify the deployed commits or deployed-source reality for:
   - analyzer-v2
   - the-critic
   - analyzer-mgmt
3. if the main local trees are dirty or lag deployed state, use isolated worktrees or deployed-source-aligned branches

Do not blindly pull or rebase into dirty working trees.
The April 11 reviews describe this isolated-worktree requirement as non-negotiable because the main local trees materially diverge from deployed state.

### Phase 2: fresh logical proof on a brand-new project

Create a brand-new project and run a fresh logical concept analysis.

Capture both ids:

- the-critic logical job id
- analyzer-v2 job id

Then verify:

1. analyzer-v2 exact artifact route returns:
   - `lookup_mode = exact_run`
   - `contract_validation_status = passed`
   - correct analyzer-v2 job id
2. analyzer-v2 latest validated route returns:
   - `lookup_mode = latest_validated`
   - the same analyzer-v2 job id
3. the-critic readback returns:
   - logical host contract
   - `_analysis_provenance.execution_owner = analyzer-v2`
   - `_artifact_authority.source_owner = analyzer-v2`
   - hosted analyzer-v2 `authority_url`
   - stable artifact hash

Then run one fresh `quick` scrutiny from the first valid logical argument:

- choose the first valid `argument_inventory` item with a non-empty `logical_form.premises` list and a conclusion

Verify scrutiny readback returns the actual response shape expected live:

- `count > 0`
- first returned row has the launched `argument_id`
- first returned row has the launched `premise_index`
- first returned row has `mode = quick`

Do not require analyzer-mgmt-style or DB-internal fields that are not currently part of the scrutiny readback payload.

### Phase 3: fresh inferential proof on the same new project

Run a fresh inferential concept analysis on the same project.

Capture both ids:

- the-critic inferential job id
- analyzer-v2 inferential job id

Then verify:

1. analyzer-v2 exact inferential artifact route returns:
   - `lookup_mode = exact_run`
   - `contract_validation_status = passed`
2. analyzer-v2 latest validated inferential route returns:
   - `lookup_mode = latest_validated`
   - the same analyzer-v2 job id
3. the-critic inferential readback returns:
   - inferential host contract
   - analyzer-v2 provenance
   - analyzer-v2 artifact-authority metadata

### Phase 4: analyzer-mgmt job-surface build and browser-backed proof

For the fresh logical and inferential analyzer-v2 jobs, treat analyzer-mgmt as a build-and-verify surface, not a verify-only surface.

That means:

- first verify in browser what the current job page actually hydrates and shows
- if required concept-artifact fields are missing or misleading, extend the job page narrowly
- then re-verify the live browser result on the same fresh jobs

Route availability or static HTML is not enough.
The proof for this phase must be hydrated browser-visible proof.

Required fields on the job page:

- validation status
- lookup mode
- analysis mode
- concept
- analyzer-v2 job id
- workflow key
- engine/chain key
- translation template key
- depth
- produced-at timestamp
- translated host artifact preview

Also verify one important negative condition:

- the concept artifact truth on the job page must not depend on generic presenter status or generic result-boundary state alone

Not required on analyzer-mgmt for this tranche:

- the-critic-only `authority_url`
- the-critic-only `artifact_hash`

Those remain appropriate on the-critic readback surface and do not need to be duplicated into analyzer-mgmt unless a concrete operator need appears.

### Phase 5: fix only the seam that the fresh proof actually breaks

If the fresh proof fails, fix only the narrow seam that the failure identifies:

- if analyzer-v2 exact/latest artifact routes fail:
  - fix analyzer-v2 artifact materialization/read seam
- if analyzer-v2 routes pass but the-critic readback is wrong:
  - fix the-critic read-through / cache / identity seam
- if analyzer-v2 routes and the-critic pass but analyzer-mgmt job page is wrong:
  - fix analyzer-mgmt concept job surface seam
- if the logical job completes and readback is right but scrutiny readback is empty or wrong:
  - fix scrutiny persistence/readback seam
- if the job itself fails before persistence or readback:
  - inspect that actual launch or analysis seam instead of assuming persistence first

Do not widen the tranche into broader architecture while fixing these issues.

### Phase 6: write the corridor closeout docs

If the fresh proof succeeds, immediately write:

1. a completion memo for the translated-artifact-authority corridor
2. a roadmap update memo describing the new current ordering
3. the next scoping memo for the following bounded corridor

## Acceptance Criteria

This tranche is complete only if all of the following are true on a brand-new project:

1. fresh logical proof succeeds end to end
2. fresh inferential proof succeeds end to end
3. analyzer-v2 exact and latest validated artifact routes both succeed for both modes
4. the-critic readback returns analyzer-v2-backed artifacts for both modes
5. the-critic readback includes correct `_artifact_authority` metadata with hosted analyzer-v2 URL and artifact hash
6. one fresh logical scrutiny run succeeds and reads back correctly
7. analyzer-mgmt job pages, in a hydrated browser session, show the concept artifact authority surface for the fresh logical and inferential jobs
8. the same analyzer-v2 job ids and analyzer-owned authority metadata can be traced consistently across analyzer-v2, analyzer-mgmt, and the-critic
9. completion memo and roadmap update are written immediately after proof
