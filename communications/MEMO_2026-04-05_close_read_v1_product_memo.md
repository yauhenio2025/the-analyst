## Purpose

Freeze the first honest `Close Read V1` product boundary.

This memo is not an implementation scope and not a general platform manifesto.
Its job is to lock five concrete product decisions now that:

- the `renderers-ui` capture-base corridor is complete
- the nested forwarding patch is live on Critic
- the material nested genealogy host consequences are already cleared on the installed package path

The decisions frozen here are:

- exact host posture
- exact V1 surface set
- exact first-hop eligibility policy
- exact routed destination set
- exact deferrals

## Product Decision 1: Host Posture

`Close Read V1` will be a **bounded Critic-hosted pilot**.

That means:

- the first V1 delivery vehicle is `the-critic`
- it will use the current Critic capture/routing runtime
- it will use the current local packed `renderers-ui` artifact workflow already proven on the live host path

This is the smallest honest posture because the current code-backed runtime evidence already lives there:

- `CaptureContext` owns live capture submission and routing
- `CaptureActionBar` owns the current visible first-hop action shell
- `V2TabContent` already threads the capture/runtime metadata into renderers
- the installed `0.6.6` package now proves nested genealogy capture on the real host path

This choice does **not** mean:

- Critic is the long-term permanent Close Read host
- the packed-artifact workflow is the long-term delivery posture
- broader thin-host architecture questions are settled

It means only:

- V1 will ship as a bounded Critic-hosted pilot because that is the currently proved runtime path

## Product Decision 2: Exact V1 Surface Set

`Close Read V1` will be **genealogy-first**.

The exact V1 product surface set is:

### Primary entry surfaces

- `genealogy_portrait`
- `genealogy_idea_evolution`

These are the primary V1 reading/work surfaces because they are the strongest current user-facing synthesis views:

- `genealogy_portrait` is the final narrative synthesis
- `genealogy_idea_evolution` is the core cross-work idea-tracing surface

### Supporting/detail surfaces

- `genealogy_target_profile`
- `genealogy_per_work_scan`

These are in V1 as supporting drill-down/detail surfaces, not as equally primary entry points:

- `genealogy_target_profile` is an intermediate profiling surface that deepens framework/concept/commitment reading
- `genealogy_per_work_scan` is a per-work comparison/detail surface

### Explicit non-V1 surfaces

Out for V1:

- AOI surfaces
- findings-bank surfaces
- research-answer surfaces as primary Close Read analysis surfaces
- any additional genealogy or non-genealogy views not named above

This does **not** deny that some non-V1 surfaces are already runtime-real or already useful.
It only freezes the first product cut around one coherent genealogy cluster.

## Product Decision 3: Exact First-Hop Operation Family

`Close Read V1` supports exactly **one** first-hop operation family:

- **capture-and-route**

That means:

- user selects or captures a current V1 section/card/item surface
- the selection is handed into the current Critic capture pipeline
- the selection is routed to one of the approved V1 destinations

`Close Read V1` does **not** include additional first-hop operation families as V1 product law, even where some runtime-real seams already exist elsewhere in Critic.

Explicitly out for V1:

- outline talking-point routing
- annotations/comments as a product-defining Close Read operation family
- findings-specific Arsenal promotion as a Close Read V1 operation family
- research-answer-specific comment/routing flows as part of the Close Read V1 product definition

Those seams remain runtime-real in the broader app estate, but they are not part of the first frozen Close Read boundary.

## Product Decision 4: Exact First-Hop Eligibility Policy

`Close Read V1` will use an **app-layer surface whitelist policy** over the current split substrate.

That policy is:

1. A first-hop capture action is product-approved only on the four named V1 genealogy surfaces.
2. On the two Critic current-renderer surfaces:
   - `genealogy_portrait`
   - `genealogy_idea_evolution`
   visible capture remains gated by analyzer-backed `first_hop_affordance.capturable === true` through `currentRendererCapture`.
3. On the two package-native nested surfaces:
   - `genealogy_target_profile`
   - `genealogy_per_work_scan`
   visible capture is accepted as V1-approved because those surfaces are explicitly included in the V1 product set and already proven on the live installed-package host path.
4. No broader inference is allowed from that package-native availability.
   - package-native capture availability elsewhere does **not** imply Close Read V1 eligibility
   - analyzer absence on those package-native nested surfaces does **not** remove them from V1, because this memo is freezing a bounded pilot product, not a converged generic capture law

This is the honest current policy because the present host law is still split across three layers:

- raw package capture in `renderers-ui`
  - requires `_captureMode` and `_onCapture`
  - does not consume analyzer `first_hop_affordance`
- Critic-local `currentRendererCapture`
  - requires `_firstHopAffordance.capturable === true`
  - does not enforce `allowed_destinations`
- `CaptureActionBar`
  - exposes the two current host actions once a selection exists

So V1 does **not** pretend that substrate convergence already exists.
It chooses a bounded product law above the current split seams.

## Product Decision 5: Exact Routed Destination Set

The exact V1 routed destination set is:

- `Arsenal`
- `Research todo`

These are the only routed destinations included in `Close Read V1`.

This is an intentional product boundary choice, not a claim that other runtime-real artifact seams do not exist.
The broader Critic runtime inventory still contains other first-hop artifact seams, but they are out of V1.

For V1:

- every approved first-hop capture operation routes into either Arsenal or Research todo
- no third routed destination is part of product law
- no per-surface destination variance is introduced in V1

This is also why the current `CaptureActionBar` remains acceptable for V1:

- it already exposes the two chosen V1 routes
- V1 is explicitly adopting those two routes only

## Exact Deferrals

The following are explicitly out of `Close Read V1`:

- Book Modeler and any other non-runtime-real downstream destination
- destination-internal lifecycle unification
- workflow-neutral destination taxonomy
- generic renderer-package capture law
- shared package / host capture-law convergence
- broad host-delivery redesign beyond the bounded Critic-hosted pilot
- AOI product inclusion
- findings-bank product inclusion
- outline talking-point routing as a Close Read V1 operation family
- annotation/comment persistence as a Close Read V1 operation family
- multi-user or multi-project architecture
- generic downstream operation law beyond bounded capture-and-route

## Why This Boundary Is Honest

This memo is intentionally narrower than the broadest runtime inventory and intentionally more product-specific than the renderer/package corridor work.

It is honest because:

- the host posture is the current proved one
- the V1 surface set is one coherent genealogy cluster already backed by current runtime proof
- the first-hop family is limited to one operation family already proven runtime-real on the host
- the routed destination set matches the current visible host action shell
- the eligibility policy is explicit about current substrate split rather than pretending it is solved

## What This Memo Does Not Claim

This memo does **not** claim that:

- `Close Read V1` is the full future Close Read product
- Critic-local runtime law is the long-term platform law
- raw package capture and analyzer-backed capture are already unified
- destination policy has become generic
- the current host should expose every runtime-real artifact seam in V1
- the broader analyzer-v2-as-brain objective is complete

It claims only:

- the first honest Close Read product cut can now be frozen as a bounded Critic-hosted genealogy-first pilot with one capture-and-route operation family and two routed destinations

## Immediate Consequence

The immediate next move after this memo should be:

- one bounded implementation scope for the Critic-hosted `Close Read V1` pilot

That scope should implement this frozen product boundary.

It should **not** reopen:

- host posture
- V1 surface-set definition
- V1 destination set
- V1 first-hop eligibility law
- the explicit deferrals above
