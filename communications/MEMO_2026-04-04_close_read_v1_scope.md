## Purpose

Execute the next step as a **docs-first product-scope memo**, not an implementation patch.

The goal is to define the smallest honest `Close Read V1` that can be scoped now that:

- the package-source capture-base work is complete
- the nested forwarding patch is live on the current Critic host path
- the two material nested genealogy host consequences are already cleared in real installed-package proofs

This slice should produce one bounded product memo that answers:

- what `Close Read V1` actually is
- what host-delivery posture it will assume
- what app-layer first-hop eligibility policy will govern visible operations
- which already-proved analysis surfaces are in or out
- which current real destinations are in or out

It should **not** jump directly to implementation.

## Why This Is Now The Next Honest Step

The renderer-substrate corridor is no longer the blocker.

The current truth is:

- `renderers-ui` package-native capture-base reuse is already landed
- `SubRenderers` adoption is already landed

- the live Critic host now consumes the refreshed `0.6.6` artifact

So the next missing work is no longer:

- package-source genericity

The next missing work is product framing:

- what lean `Close Read V1` should include
- and what it should explicitly leave out

## Scope

### 1. Choose one explicit host-delivery posture

The product memo must choose one concrete host posture, not leave it implicit.

At minimum, it must decide between:

- a bounded Critic-hosted pilot posture
- or a different thin-host posture that is still realistic against the current codebase

Default calibration:

- bias toward a bounded Critic-hosted pilot unless code evidence shows that is dishonest

Reason:

- current runtime evidence, current capture/destination seams, and the newly proven nested genealogy surfaces all live on Critic today

The memo must state plainly:

- why that posture is the smallest honest V1
- what it inherits from the current host
- what it does **not** settle about broader long-term delivery architecture

### 2. Define the minimum V1 analysis-surface set

The product memo must identify a bounded initial surface set grounded in already-proved runtime reality.

The default candidate center of gravity should be genealogy, because it now has the deepest contiguous current proof line across:

- `genealogy_target_profile`
- `genealogy_per_work_scan`
- `genealogy_portrait`
- `genealogy_idea_evolution`

But the memo should not assume that all four are equally core V1 surfaces.

Default calibration:

- treat the four-view genealogy set as the current proved product cluster
- distinguish likely primary V1 entry surfaces from broader supporting/detail surfaces inside that cluster
- bias toward:
  - likely primary V1 surfaces:
    - `genealogy_portrait`
    - `genealogy_idea_evolution`
  - likely secondary/detail surfaces:
    - `genealogy_target_profile`
    - `genealogy_per_work_scan`

AOI findings surfaces may be mentioned only if they materially strengthen the first V1 and are justified from current runtime proof rather than breadth-for-breadth's-sake.

The memo must distinguish:

- required V1 surfaces
- optional later expansions
- surfaces explicitly deferred

### 3. Define the first-hop operation and destination set

The memo must stay bounded to **current real first-hop operations** only.

For V1, the routed destination set should intentionally be limited to:

- Arsenal
- Research todo

That is a V1 boundary choice, not a claim that no other runtime-real first-hop artifact seams exist in the current app estate.
The runtime inventory already documents other real first-hop artifact seams in Critic, but this memo should treat them as intentionally out of scope for the first product cut unless a stronger code-backed reason is given.

Do not widen V1 to:

- Book Modeler
- destination-internal lifecycle unification
- generalized async research lifecycle policy
- workflow-neutral destination taxonomy

The memo must say explicitly whether `Close Read V1` is:

- capture-and-route only
- or capture-and-route plus any additional first-hop operation family already proven runtime-real

If it claims more than capture-and-route, it must point to current runtime evidence.

### 4. Define one explicit app-layer first-hop eligibility policy

The product memo must resolve the policy question that renderer/package work does **not** settle by itself:

- visible package capture affordance is not automatically the same thing as app-approved `Close Read` action eligibility

Current capture/eligibility law is still split across three host layers:

- raw package capture in `renderers-ui`
  - gates only on `_captureMode` plus `_onCapture`
  - does not consume analyzer `first_hop_affordance`
- Critic-local `currentRendererCapture`
  - requires `_firstHopAffordance.capturable === true`
  - but still does not enforce `allowed_destinations`
- `CaptureActionBar`
  - exposes the current two host actions once a selection exists

So the memo must specify one bounded app-layer policy for V1.

At minimum, it must answer:

- when should a visible capture operation appear in `Close Read V1`
- what role analyzer-owned `first_hop_affordance` plays where it already exists
- how raw package capture availability on nested surfaces interacts with app-level product law
- whether V1 will allow only destinations that are currently real and already routed by the host

Default calibration:

- do not invent generic destination policy
- do not assume raw package capture availability alone is sufficient
- do not assume currentRendererCapture plus CaptureActionBar already provide one converged product law
- keep V1 beneath generic renderer-package capture law

### 5. Name the explicit deferrals

The memo must keep these explicitly out of V1:

- Book Modeler and other non-runtime-real destinations
- destination-internal lifecycle unification
- workflow-neutral destination taxonomy
- generic renderer-package capture law
- shared package / host capture-law convergence
- multi-user or multi-project architecture
- generic downstream operation law beyond what current runtime evidence supports
- broad host-delivery redesign beyond the chosen bounded posture
